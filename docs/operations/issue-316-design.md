# Native subscription companion design

Status: implementation in progress; #316 remains open. Repository: `Vinosaamaa/chanter`. One native-companion lane and one final issue-linked PR. Accepted baseline: `798eb16cd1f505b6378ff6241cd3c16a430e74ff`. Backend integration waits for #244; learner UI coordination belongs to #321 and #254. No paid inference is authorized.

## First supported path

Run the user's unmodified Codex executable as a private stdio child. A companion-owned provider home separates this integration's provider-managed login from the user's existing tools, plugins, instructions, and sessions. Only Codex reads/writes its authentication store. Chanter never imports credential files, handles external ChatGPT tokens, or sends subscription credentials to its backend. Start login only after the local user chooses the provider-owned browser or device flow. Do not log URLs containing login state, device codes, account identifiers, messages, or raw provider errors.

Compatibility starts with the locally inspected CLI 0.153.4 schema. Unknown versions fail closed until protocol and isolation tests pass; version detection alone does not prove isolation. Account discovery exposes a sanitized authentication category and plan, then provider-advertised models and limit windows. API-key accounts are rejected. External-token login/refresh is never exposed; managed-auth provenance comes from the private stdio method allowlist and isolated provider-owned store, not the `account/read` ChatGPT category alone. Missing usage is unknown. A plan label is not proof that the next request is free or permitted; provider limits and account policy remain authoritative. Never buy credits, enable overage, redeem reset credits, or silently fall back to an API.

## Request boundary

The browser talks to a fixed, loopback-only companion endpoint after explicit native pairing. Pairing binds the exact configured HTTPS Chanter origin and the current Chanter user/session to a random installation secret. The secret stays native; the browser receives an expiring pairing handle. Every non-preflight request checks the literal loopback Host and exact Origin and requires a non-simple authenticated request. CORS permission is not authentication. Re-pairing and logout revoke handles. No arbitrary URL, executable, filesystem path, Codex RPC method, environment variable, or provider credential may arrive from the browser.

Before releasing evidence, the backend checks current Course/channel grants, resource availability and approval, installation grants, and explicit approval to export that request to Codex. It atomically reserves the request's budget and emits a short-lived signed capability binding the user/session, question, provider/model, mode, evidence hashes, input/output bounds, and expiry. The companion validates the signature against the configured Chanter deployment key, requires local user approval of that provider/request, and consumes the capability once before transport. Process restart must not make consumed capabilities reusable. Unknown completion retains the attempted-generation claim from #248; only a proven pre-transport failure permits retry.

Result acceptance repeats current authorization and evidence-content checks. Client-submitted text and usage are untrusted. The backend validates citations and mode-specific evidence before saving; provenance identifies a native client report and cannot become an authoritative bill. Saved questions remain immutable; Source only is the safe recovery path after an uncertain attempt. Grounded explanation remains blocked on #247/evaluation, and quoted evidence remains visibly extraction.

### Implemented native contract

The internal listener binds only `127.0.0.1`, defaults to port 43160, and exposes only `POST /study` and its exact-origin preflight. Pairing is a direct native UI action, with no browser pairing or generic RPC route. The listener rejects wrong/duplicate Host or Origin, simple content types, absent pairing headers, extra JSON fields, and bodies larger than 144 KiB. It caps connections, header/body timeouts, and framed output. Closing the HTTP response cancels the native turn. The unsigned developer launcher supplies a visible terminal with expiring random approval challenges; redirected input cannot approve. Importing this module alone starts no service.

The native deployment configuration supplies an Ed25519 public key and the exact HTTPS origin. A ticket is unpadded base64url JSON followed by a dot and an unpadded base64url Ed25519 signature. The signed bytes are the UTF-8 string `chanter-native-v1.` followed by the encoded JSON. Tickets are at most 12,000 characters, live at most 120 seconds, reject unknown fields, and bind `version=1`, `kind`, `installationId`, `origin`, `userId`, `sessionId`, `requestId`, `issuedAt`, and `expiresAt`. Time fields are Unix milliseconds. Study tickets additionally bind `questionId`, `provider=codex`, `mode=quoted-evidence`, `model`, `promptSha256`, `evidenceSha256`, `maxInputBytes`, `maxOutputBytes`, and `deadlineMs`. The prompt hash covers the exact UTF-8 input. The backend must construct that input from its authorized evidence before signing. The native boundary cannot independently establish course membership or evidence approval.

The installation secret and durable claims live in a private SQLite database. Windows creation uses the current user's explicit protected access rules and rejects broadened permissions, reparse points, hard-linked database files, or a different owner on reopening. POSIX code requires current ownership and private directory/file permissions; it has not yet been exercised on a native POSIX provider. The database stores no provider credentials or course text. Pairing stores a secret-keyed digest of a random handle and binds the exact origin/user/session. Re-pairing replaces the previous handle; logout revokes it. Native approval expires with the ticket, and request execution rechecks expiry and current pairing afterward. A SQLite immediate transaction commits the one-use claim before provider transport. Claims survive process restarts and are never removed for a retry; a 10,000-claim limit fails closed until the lifecycle/retention policy is completed.

These signatures currently come from synthetic test keys. Backend issuance, atomic account-budget reservation, signing-key provisioning/rotation, live session revocation, and result acceptance remain pending the accepted backend baseline. The native launcher verifies the provider version and checks subscription authentication, advertised model, and known unexhausted primary and secondary limits before inference. A public API key, browser input, or plan label cannot satisfy that requirement. This boundary still needs consenting eligible-account verification.

## Isolation gate

The provider process starts in an empty directory with an explicit environment allowlist, separate provider home, strict configuration, no inherited MCP servers, apps, hooks, plugins, host skills, memories, browser/computer tools, shell, code execution, image access, web search, or subagents. Use supported controls and inspect the effective response; do not rely on prompt instructions. The available experimental `environments: []` field disables environment access according to the generated 0.153.4 protocol schema, but must be exercised before treating it as a security boundary. Permission profiles can further deny filesystem/network access to tools while leaving provider-owned authentication intact.

Inference remains unavailable until native tests prove the exact restricted tool surface and rejection of canary reads outside the empty workspace, including the provider-home boundary. CLI 0.153.4 retains the `skills` namespace despite disabling skill discovery and instructions. Native loopback tests establish empty orchestrator/executor catalogs even with a planted host skill, refusal of a forged absolute-path package/resource, and refusal of an unadvertised shell call. A future changed tool surface must fail compatibility checks; this is not a claim of literally zero tools. Deny every unexpected server tool/approval request. An output cap, deadline, cancellation signal, and process termination bound apply even after protocol failure. Provider-managed authentication traffic is distinct from tool network access. Never relax a managed administrator restriction to make this integration work.

## Delivery slices and evidence

1. Vertical tests for sanitized status, managed login, paginated models/limits, stdio bounds, timeout/disconnect, and unsupported versions; then a real no-login/no-inference native handshake.
2. Native isolation and tool-surface fixtures, ephemeral transcript behavior, cancellation, bounded result/usage mapping. A synthetic local provider transport may test the unmodified binary without sending course content or using paid inference; it does not prove subscription entitlement.
3. Loopback pairing, durable one-use capabilities, replay/DNS rebinding/origin/request tampering tests, and backend authorization/reservation integration after dependencies land.
4. Learner integration, provider-owned login and eligible-account native end-to-end verification, installer signing/versioning, and release receipts. Do not describe unsigned developer builds or protocol fixtures as a completed installable product.

The complete security test plan covers malicious websites, spoofed Origin from a non-browser without pairing, wrong Host, expired/replayed capabilities, mismatched evidence/model/result, revoked membership, concurrent reservation, inherited tools, provider failure, cancellation, and uncertain completion. No content or credentials enter public evidence. Transcript retention is intended to be memory-only for study requests. The native fixture confirms `ephemeral=true` and upstream `store=false`, but Codex still creates operational SQLite databases. Those flags alone do not prove that every operational log is content-free or that the provider retains no data. Audit the operational data and define deletion before release; never upload provider session files as evidence.
