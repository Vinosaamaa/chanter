# Issue 316 review follow-up

PR #324 remains a draft. The first full CodeAnt review covered `a13fb233680824d01e020305871de175b60eb625`; automatic quality/security statuses are separate from that review.

- Unknown plan: confirmed. A ChatGPT account with missing/unrecognized plan now has unsupported authentication status and cannot reach discovery/inference. Account boundary tests cover absent, null, and future plans.
- Cleanup replacement race: recursive removal was avoidable. Cleanup now snapshots entries, rechecks canonical paths and filesystem identity, and removes only individual inspected files and empty directories. New children cause failure rather than recursive deletion. A linked-descendant canary stays untouched. The private state root and verified provider exit exclude untrusted concurrent writers in the supported boundary; this does not claim protection against a hostile process running as the same OS user, which can also replace the application, signing key, or database.
- Interrupted installation: preserved state is intentional. Recovery uses a new empty installation directory, documented in the operator instructions. Automatic overwrite/deletion of an ambiguous partial installation would weaken the state boundary. This is a developer-package limitation, not a completed upgrade/uninstall mechanism.
- Consumed-claim capacity: the 10,000-claim fail-closed limit is intentional pending the final backend/lifecycle policy. Expiry alone does not release an uncertain attempt. No request is silently retried or forgotten. This availability gate remains explicit in #316 and must be resolved before general release.
- Hosted Windows ownership: Windows can assign an elevated process's default group as the owner of new objects. Exclusively created database/program/runtime-root entries now receive current-user ownership after verifying private access rules. Existing entries are never repaired. Broad-access reopen tests remain mandatory.

Other suggestions concern bounded-buffer allocation, helper extraction, repeated version probes, terminal command buffering, and synthetic test-directory cleanup. They do not establish additional browser-to-native authority. Existing frame/body/deadline/connection bounds remain enforced; version checks deliberately repeat to detect replaced binaries. Synthetic local fixtures remain ignored and contain no credentials or real evidence. Refactoring and fixture housekeeping can follow after the security and product contracts stabilize.

The second full review covered `f3a23e2e3f6027c55be2c4c56d6a85c3941a765c`. It added a failed-run-creation finding: if marker creation fails before any provider exists, the creating call now attempts inspected cleanup of only its own new directory. Any retention failure blocks the provider instance. Startup still refuses an ambiguous unmarked orphan, because a later process cannot prove who created it or whether an unrecorded provider is alive.

The Free-plan finding is not an entitlement bypass: OpenAI's [current plan guidance](https://help.openai.com/en/articles/11369540-using-codex-with-your-chatgpt-plan) includes Free and Go access. Recognized plan names classify provider-owned ChatGPT authentication; each call additionally requires the provider-advertised model and known unexhausted windows. The internal `subscription` category is not a claim that the account pays a subscription or that every account is eligible. Unknown plans still fail closed. Recheck individual eligibility before real inference.

## Durable reconciliation review

The review at `8d4566c` identified the same failure-after-save defect in the hosted answer path. Hosted and source-only saves now use the same atomic answer/status-event transaction as native answers. Existing-answer recovery repairs a missing event under an answer-row lock and never retries the provider. The existing outbox remains the only delivery/retry mechanism. Regression coverage includes downstream HTTP503, repeated answer requests, and concurrent legacy repair.

The design now distinguishes the atomic budget reservation from later signing and metadata persistence. Failure after reservation retains the attempt; it does not imply those stages share a transaction or that a provider attempt can be retried. The retention test now separately exercises an unrecognized directory and verifies its canary survives, rather than claiming that coverage from the active-run test.

The remaining suggestions do not reveal new authority or consistency defects. The shared #245 consumer intentionally serializes the small launch-scale projection transactions; replacing its global lock or retry implementation is outside this change. Delivered event payloads are redacted, while identifiers and cursors retain replay authority under the existing event-retention policy. Test-only synthetic directories remain ignored. Prior dispositions for consuming status tickets before discovery, failing closed on retention errors, and repeated binary verification still apply. Broad helper extraction, alternate indexes, and packaging optimization are not prerequisites for this bounded contract.

The full review at `56f0c9f` found two additional failure classifications. Legacy status repair now rolls back independently and leaves an already-saved, currently authorized answer successful. A later authorized request can append the missing event through the same outbox, without another provider call. The HTTP regression injects failure after the real append, verifies rollback and the same successful answer, then verifies exactly one repaired event. Native result validation now retains timeout, cancellation, refusal, and other known outcomes instead of recording every exception as INVALID_RESPONSE. Each outcome retains UNKNOWN usage, the full budget reservation, and rejection of replay or a new generation attempt.

The proposed requirement to echo the browser-visible signed ticket at result submission would prove possession, not provider execution. The accepted boundary instead checks the live session, current grant and source evidence, immutable server request scope, atomic request claim, and replay rejection. Native execution and token counts remain client reports; neither the API nor usage accounting treats them as verified provider provenance. A device attestation protocol is not introduced by this change.

The review at `4408c5b` found a further failure-after-save path in native settlement. Once answer persistence succeeds, failed ledger or request-finalization bookkeeping no longer replaces its successful response. Existing request/reservation rows keep replay and new attempts blocked; scheduled evidence redaction and conservative unknown-usage handling still apply. Fault-injection tests cover both writes, and the native HTTP fixture verifies a real saved answer remains readable after settlement failure. The separate post-reservation issuance-failure finding retains the documented conservative behavior: uncertainty consumes the attempt and source-only recovery remains available.

Saved-answer audit responses now label native execution CLIENT_REPORTED. The UI says “Reported by your desktop app. Token usage unavailable.” The server-provider label SERVER_OBSERVED means this service received that provider response, not that an external party attested execution. API tests distinguish native, hosted, and source-only provenance; frontend tests cover both the explicit field and legacy native-answer fallback.

Review at `a04a59a` correctly extended settlement failure preservation to rejected results. A later bookkeeping failure must not replace the original invalid-quotation, revoked-access, or timeout response. Six combined-failure regressions now cover both bookkeeping writes and those three original failures; usage stays unknown and claim/reservation rows reject replay and new attempts.
