# Issue 245 system review

The source service owns each mutation and event in one transaction. Notification owns recipient state, and search owns a disposable projection. Delivery uses fixed configured HTTP destinations and the existing internal service token. Event identity, schema version and revision are durable database values. One small shared implementation serves repeated source queues and consumer cursors; source payload construction and authorization remain in their modules.

At-least-once delivery is explicit. Claims expire after 60 seconds, requests time out after five seconds, and stale workers cannot acknowledge a replacement lease. Eight failed attempts produce an inspectable failed row. Replay preserves event identity/revision and records its count/time. A dedicated scheduler keeps consumer outages from blocking media lifecycle jobs. Consumer receipt and projection changes share a transaction and database lock; permanent deletion cursors defeat either delivery order and manual legacy repair cannot overwrite event-managed sources.

Search never treats an index row as authorization. Navigation restricts Course candidates; resource/FAQ catalogs and exact event/announcement/message reads enforce current access. Event scope changes suppress stale snapshots. Inbox list/count/read/done also recheck the source with the recipient identity, exclude revoked or archived content, and fail explicitly during source outages. Internal event and outbox operations have no public gateway route. The new exact-message lookup is called directly by search-service with delegated identity, not by the browser.

Source database migrations add community V18, message V9 and media V3 outboxes. Notification V2 and search V2 add durable cursors; search allows Study Server results without a Course. Agent migrations are untouched. Deploy only under compatibility epoch 5. Do not roll back to an earlier epoch after this contract is active; use a compatible release with retained database state. Production wiring is coordinated with #243.

Operator inspection is `GET /api/v1/internal/events/outbox`, with counts, oldest pending timestamp and last successful delivery. `GET /failed` returns up to 100 failed identifiers and sanitized error codes. `POST /{id}/replay` accepts failed records only and cannot change their destination. These routes require the internal service token on the source service. Inspect failure cause and destination health before replay; repeat inspection after replay to confirm delivery. No message body or token appears in inspection responses.

The free single-host design serializes short consumer transactions and bounds each dispatcher pass to 25 deliveries. Inbox live checks scale with distinct unread sources; request-local reuse avoids repeated checks of the same source, database reads are paged, and HTTP checks do not hold database transactions. Course/Cohort event recipient selection is one scope-authorized query. Retention/backups remain coordinated with #251. Existing data is retained, and the legacy authorized resource/FAQ repair route remains compatible; automatic delivery applies to supported source mutations after upgrade. Historic message/event backfill is not claimed by this change.

Required evidence separates fast H2 regressions, PostgreSQL concurrent claims/apply tests, a process outage/restart drill using the actual product databases, and rendered browser journeys. PostgreSQL concurrency and the actual drill passed on the initial PR head. The drill proved source writes while both consumers were stopped, update/archive convergence, unique Inbox delivery, persisted read state and search after a second restart. Its browser follow-through required an Inbox locator correction. Fixture screenshots at 390 and 1280 pixels were inspected separately.
